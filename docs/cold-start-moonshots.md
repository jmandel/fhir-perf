## Duplicate kill (merge map)

- **HERMETIC-GATE / GREEN-BUILD PROMOTION**: lens1#5, lens5#5 — merged into ANSWER-PACK's supply chain; a pack without an enforced completeness check and an rc=0 promotion gate is just a cache with better PR.
- **FRAGMENT/SUBSET SHIPPING**: lens2#4, lens3#5, lens5#4 — merged, then rejected (below).

Secretly-re-proposes-tried-list kills: **syntactic speculation prefetch** (lens6#1) is the done expansion-prefetch plus the parked $batch dry-pass with a cheaper question collector — it still fires ~1,900 requests at tx.fhir.org every cold build (politeness-neutral at best, worse with overspeculation) and is strictly dominated by a pack that fires zero. **Fork-fallback zip** (lens6#6) is a 1-day patch that deepens the mutable ~/.fhir/tx-cache mechanism the owner wants dead; its one good component (the poison-signature filter) migrates into the pack recorder.

## Survivors, attacked

**1. ANSWER-PACK (tx.lock: committed/content-addressed recorded answers, read-only seed layer in TerminologyCache, success-only recording, hermetic CI gate, green-build-gated refresh PRs).**
Attacks that stick: (a) It IS recorded server bytes — legitimacy rests entirely on the owner's lockfile distinction; every property (immutable, hash-keyed, explicit refresh, errors-unrepresentable, reviewed diffs, enforced completeness) must actually ship or it's a renamed cache. (b) Key fragility: TerminologyCache keys embed pretty-printed serialized ValueSets — any fhir-core serialization or CACHE_VERSION change silently invalidates the whole pack. Degrades to today's behavior (full network), not to wrongness, but the failure is a 415s build with no error; the hermetic gate is what makes that loud — that's why the gate is non-optional. (c) Staleness absorption: a pack hit never consults the server, so tx.fhir.org curation changes are invisible between refreshes. Honest answer: that's today's warm-cache behavior too, and the weekly replay-diff PR makes drift *more* visible than the status quo, not less. (d) Refresh ownership: edition bumps produce a multi-MB reviewed diff someone must own; multi-system requests (204) whose keys embed VS content will drip misses on every VS-touching PR. Survivable but must be budgeted. Score: impact 10/10 (-200s remote, the entire measured gap, plus variance→0), parity 9/10 (identical code path to the proven warm-cache replay), effort medium, dependency: data-artifact.

**2. UCUM-TABLE (commit the server's curated display table + BCP-47/mimetype, wired into the live localFirst gate).**
Attacks: (a) Same staleness-absorption hole as the pack, smaller surface — needs the same replay-diff loop. (b) The self-refresh-on-miss write-back is mutation into the repo; it must go through reviewed PRs from clean runs, not silent saves (tighten the snomed.xml precedent, don't just copy it). (c) Envelope parity is the real work: the warning text embeds server phrasing, and H1-H3 proved the synthesis path is verifiable byte-for-byte — gate on 851/851 corpus match or don't ship. (d) It's subsumed by the pack — but it's days not weeks, it survives even if tx.lock stalls politically, it shrinks the pack and refresh manifest by ~45%, and it has 20 years of in-repo precedent. Score: impact 6/10 standalone (-31% requests, -40-65s remote), parity 9/10 (byte-verified against existing corpus before shipping), effort small, dependency: data-artifact (tiny, in-repo).

**3. EVAL-MEMOIZATION (run-scoped content-keyed memo of local terminology evaluation, lens1#4).**
Attacks: (a) Result aliasing — if any caller mutates a returned ValidationResult/expansion, memo sharing corrupts later answers; needs defensive copy or audited immutability, which is exactly the kind of bug the adversarial pass on spike A existed to catch. (b) The expParameters-copy trap is mapped but proves the keying must be content-derived, not identity-derived — easy to get subtly wrong and silently lose all hits (wallclock-neutral failure, like the dead first memo). (c) Zero philosophical exposure: in-memory only, pure function, no persistence — the only idea with no cache debate at all, and the only lever on the cold-local/warm floor that everything else converges toward. Score: impact 5/10 (-40s local, -20-40s remote, compounds with everything), parity 8/10 (by construction, modulo concurrency bugs), effort medium, dependency: code-only.

**4. DETACH-VERDICT (pages ready at produce-complete, validation verdict lands after, lens4#1).**
Attacks: (a) It changes the developer contract — "site ready" before Errors=0 is known invites trusting dirty trees; late checkAllOk semantics are a real design problem, not a detail. (b) Its headline gain (-200s perceived on cold-remote) is mostly the same seconds the pack removes for real; post-pack it's worth maybe 20-40s of pages-ready. (c) Final tree byte-identical, genuinely. Verdict: real, code-only, but do it after the pack, when its residual value is measurable. Not top-3.

## TOP 3 SPIKES

**Spike 1 — UCUM-TABLE (do first, it's days).** Extract the 851 unit→display pairs (plus 117 BCP-47, 33 mimetype) from the existing H1-H3 captured corpus into tools/tx/ucum-displays.xml using the snomed.xml format; wire lookup into the spike/core-localfirst gate on the path ValueSetValidator actually calls (not the dead BuildWorkerContext overload); synthesize responses with the existing byte-verified envelope machinery. Gate: synthesized-vs-captured byte match on all 1,001 entries before enabling; then paired same-window cold-remote runs + judge.sh. **Success: Errors=0/Warnings=3693, manifest clean, ≥850 fewer unique requests, measured wallclock delta reported honestly (expect -40 to -65s remote).** Kill criterion: any envelope mismatch that can't be normalized — then the class falls back to Spike 2's pack.

**Spike 2 — ANSWER-PACK + HERMETIC-GATE (the flagship; gate ships in the same spike or not at all).** Add a read-only seed layer to TerminologyCache (load() path exists), consumed before the mutable layer, misses falling through to network and logged as derivation keys. Record the pack from one clean rc=0 cold run (serial, off-peak, polite; recorder structurally rejects non-2xx/transient outcomes — the measured poison class becomes unrepresentable). Add -Dorg.hl7.fhir.tx.hermetic at the ManagedFhirWebAccessor choke point. Then run cold-hermetic against the pack. **Success: build completes hermetic with empty miss list, cold-remote wallclock ≈ warm (~212s), judge.sh byte-clean vs reference; secondary: a deliberately-edited ValueSet produces a miss (proves staleness-by-key, not staleness-by-trust).** Kill criterion: key canonicalization can't be made stable across runs (hit rate <95% on replay of the recording run itself).

**Spike 3 — EVAL-MEMOIZATION.** On spike/core-txperf: intern sha256-of-canonical-JSON per ValueSet/CodeSystem on userData at load; key = (vsHash, csHashes, content-derived paramsHash, op) → run-scoped ConcurrentHashMap of evaluation results, with defensive copy on return; params hash computed from canonical content (the mapped expParameters trap). Re-run spike A's adversarial concurrency review. **Success: cold-local 240s → ≤205s, study-design VS expands once, Errors=0/Warnings=3693, A/B manifest diff clean across 3 runs (concurrency soak).** Kill criterion: hit rate near zero (keying trap repeated) or any CME/aliasing the serial-retry net can't contain.

Sequencing logic: 1 is the cheap upstream-palatable proof of the replay philosophy; 2 is the win; 3 is the only thing that moves the floor both converge on. Stacked endpoint: cold = ~195-205s, anywhere, any hour, zero tx.fhir.org traffic from dev builds.

## Best long-term bet

**Hermetic pack derivation: FHIRsmith-in-CI as the pack builder (lens1#2).** Recording mode (Spike 2) ships first but its provenance is "bytes tx.fhir.org said once." The endgame is the pack as a reproducible derivation: inputs = (FHIRsmith rev, edition pins, request manifest), builder runs only in CI, output hash independently rebuildable, promotion gated on judge.sh byte-parity — at which point production tx.fhir.org receives zero requests from this repo, ever, and "is the pack right?" becomes bisectable instead of trust-me. The pack format is agnostic to producer, so this swaps in behind Spike 2 without touching the client. The measured edition-skew (binding-annotation text) is exactly what the promote-on-clean-diff gate exists to catch; until pins match, divergent systems stay on recorded bytes and tx.lock records which entries came from where. The standards-track variants ($prepare-publication, $dump-displays) are the ecosystem version of the same thing — worth proposing to Grahame once the client half is proven, not before.

## REJECTED

- **Content-addressed GET /expansions + CDN** (lens3#2): requires the tx.fhir.org team to spec and maintain a canonicalization function; the pack gets the same answers with zero server work.

- **SNOMED/LOINC fragment packages / membership compiler / $extract-subset** (lens2#4, lens3#5, lens5#4): licensing blocker plus the weakest parity story in the set (engine equivalence vs verbatim replay) for request classes the pack already covers; months of work to handle never-seen codes the spec, by census, doesn't ask about.
- **IANA registry pinning** (lens2#5): ~6% of traffic, nontrivial display-composition rules; fold the 150 captured answers into Spike 1's table instead.
- **Syntactic speculation prefetch** (lens6#1): still pays ~1,900 tx.fhir.org requests per cold build; re-proposes the prefetch/dry-pass lineage; strictly dominated by zero-request replay.
- **CRaC/CRIU heap checkpoint** (lens6#4): an opaque unreviewable binary blob fails the owner's lockfile honesty test on every axis (not diffable, not reproducible, not auditable); Linux/JDK-specific; only helps same-key rebuilds. The 80s load phase is real but earn it with profiling, not process snapshots.
- **Fork-fallback tx-cache zip** (lens6#6): one day of effort invested in the mutable-cache mechanism being retired; the poison filter survives inside the pack recorder.
- **Incremental validation / cross-builder verdict ledger** (lens4#5, lens6#5): key-completeness discipline (suppressed messages, options, context fingerprint) is a large silent-wrongness surface; high effort; revisit as phase 2 once the pack proves the gated-supply-chain pattern — it's the same philosophy one level up.
- **Detach-verdict** (lens4#1): genuinely good and code-only, but it changes the verdict contract and the pack erases most of its gain; queue behind the top 3, measure residual value then.

# Raw ideas by lens


## Lens: Bazel/Nix build-system designer: terminology answers as content-addressed derivations over hermetic inputs; memoization as pure-function evaluation; network as an impurity to be sealed off and verified, not merely reduced. The key structural observations: (a) the spec already pins versioned editions, so every tx answer is a pure function of committed inputs — the build just doesn't model it that way; (b) the repo already ships small committed answer files (tools/tx/snomed/snomed.xml), so the lockfile pattern has precedent; (c) the current TerminologyCache keys embed full serialized ValueSets, i.e. it content-addresses by accident and pays serialization instead of hashing; (d) the owner's mutable-cache objections (poisoning, branch-keying, staleness) are all properties of mutation and implicit refresh, none of immutable hash-addressed artifacts with explicit refresh and enforced completeness.

### tx.lock: a content-addressed, read-only terminology answer pack consumed as a sealed dependency
- **Mechanism:** Model every terminology operation as a derivation: key = sha256(operation, canonicalized request with inlined ValueSet content replaced by sha256-of-canonical-VS-JSON, code-system edition pins, expansion params). Ship a single immutable pack file (zip or CDB; filename = sha256 of its contents) containing key -> exact-server-response-bytes for the ~1,900 unique validate requests and ~800 $expands, referenced from a tiny committed tx.lock {packHash, txServerSoftwareVersion, edition pins, date}. Hook point: a new read-only AnswerPack layer in fhir-core between TerminologyCache miss and TerminologyClientManager network fallthrough (the exact seam the warm disk cache already exploits). Misses fall through to tx.fhir.org exactly as today AND are appended to a staleness report listing the missing derivation keys; a separate explicit `refresh-tx-lock` job regenerates the pack. Recording rule enforced structurally: only 2xx semantic outcomes enter the pack — transient errors, timeouts, and 404-shed responses are unrepresentable, which deletes the cache-poisoning failure class the owner rightly fears. The pack is fetched by hash like a Maven artifact; nothing ever writes to it.
- **Cold impact:** Cold-remote 415s vs warm-remote 212s = ~203s gap that the facts attribute to terminology round trips. A complete pack answers all ~2,700 requests locally, so cold-remote -> ~212s (-200s, -49%). Bonus: removes tx.fhir.org's ±40%-by-hour variance from cold builds entirely. Cold-local barely moves (network already 1ms); see the memoization idea for that gap.
- **Parity:** The pack stores the server's literal response bytes for pinned editions; consuming them follows the same code path as a warm tx-cache hit, which is already proven at Errors=0/Warnings=3693. Because ValueSet content is part of the key (by hash), any spec edit that touches a VS misses the pack and goes to the network — answers can be slow-but-fresh, never stale-but-wrong. Honest caveat: this IS recorded server output shipped as data; its legitimacy rests on the owner's accepted lockfile distinction — immutable, hash-verified, explicit refresh, success-only — every property the mutable ~/.fhir/tx-cache lacks.
- **Effort:** Medium: ~1-2 weeks. Canonical keying + pack format + read hook in fhir-core (~500 LoC), a --record-tx-pack mode reusing the existing request/response capture harness from the H1-H3 census, CI publish step. The parked two-pass $batch machinery (spike/core-batch-tx, 1,424 misses -> 102 POSTs) is the ideal *refresh-job* engine: its 15x request reduction matters for politeness there, and its wallclock-negativity is irrelevant offline.
- **Novelty:** Differs from persistent disk caching (immutable, content-addressed, versioned, success-only, explicit refresh vs implicit mutation), from cache-id (no protocol change — full requests still formed, just answered locally), from $batch prefill (no build-time network restructuring; the parked work is repurposed as the offline generator), and from FHIRsmith colocation (no server process for devs — the pack is a file). The spec repo already commits exactly this pattern at small scale: tools/tx/snomed/snomed.xml (81KB, 625 concepts) — this generalizes it to the full request space with content-addressed integrity.

### Build the pack as a hermetic derivation: FHIRsmith-in-CI as the builder, not a dev dependency
- **Mechanism:** Instead of recording tx.fhir.org responses, define the answer pack as a reproducible derivation in the Nix sense: inputs = (FHIRsmith git rev, terminology data library pins from data/tx-local.yml — SNOMED intl 2024/2025 + US, LOINC 2.82/2.77, the curated UCUM display table, hl7.terminology 7.1.0), build action = boot FHIRsmith in a container and replay the request manifest (the derivation-key list from the census, or emitted by a hermetic-mode build's miss report), output = pack file. Same recipe + same pins = same pack hash, so anyone can independently rebuild and verify it. The owner's objection to FHIRsmith was 'don't require a local server for dev' — here the server runs only inside the pack-build job; developers consume a file. Refresh loop: bump the data pins in tx-local.yml, rebuild pack, run runs/judge.sh against the reference manifest; zero requests to production tx.fhir.org ever (maximal politeness).
- **Cold impact:** Same arithmetic as tx.lock (it is its supply chain): cold-remote 415s -> ~212s. Additional payoff: pack regeneration costs tx.fhir.org nothing, and the cold-local FHIRsmith result (240s, rc=0, 1,930 requests at 0-2ms) already proves the builder produces build-grade answers end to end.
- **Parity:** Membership/expansion is a pure function of (VS definition, code system edition, params) — the measured fact that makes this sound. The known risk is edition skew: findings recorded small metadata differences between local FHIRsmith data and production (binding annotations like '(a valid code from https://www.iana.org/time-zones)'). Mitigation is the existing byte-level gate: judge.sh + ref.manifest diff must be clean before a pack hash is promoted into tx.lock; a skewed pack is rejected at generation time, not discovered downstream. Until pins fully match production, fall back to recording mode (idea 1) for the divergent systems — the pack format is agnostic to how entries were produced, and tx.lock records which.
- **Effort:** Medium: FHIRsmith already runs locally with imported data (~40s boot); work is containerizing it, a replay driver over the derivation-key manifest, and the promote-on-clean-diff CI gate. Largely orthogonal to the fhir-core hook, so it parallelizes with idea 1.
- **Novelty:** The tried item was 'colocated FHIRsmith server' as a runtime dependency — rejected for dev ergonomics. This inverts it into a build-time-only oracle whose output is shipped. Nothing in the tried list treats terminology answers as a reproducible derivation with verifiable provenance; this also converts future 'is the pack right?' disputes into a bisectable recipe instead of trust-me recorded bytes.

### Vendor the UCUM curated display table as committed derived data (kills the single largest request class)
- **Mechanism:** UCUM display-checks are 851 of ~1,900 unique validate requests (45%), and H1-H3 skipped them with evidence: tx.fhir.org uses a curated display table the local UCUM library provably cannot reproduce (530/851 mismatches). So ship the table itself: extract the 851 unit->display answers either from FHIRsmith's source data (it is tx.fhir.org's implementation — the curated table exists as data in that repo) or by one polite serial recording pass, and commit it alongside the existing precedent files as e.g. tools/tx/ucum/ucum-displays.xml (~50-80KB, smaller than the already-committed snomed.xml). Wire it into the existing localFirst gate (spike/core-localfirst @ d7f9f3e06, -Dorg.hl7.fhir.tx.localFirst): table hit -> synthesize the validate-code response locally via the byte-verified synthesis machinery already built for unknown-system responses; table miss (new unit in a spec edit) -> network fallthrough, plus a line in the self-refresh pass that PageProcessor already runs for snomed.xml/loinc.xml (PageProcessor.java:10548-10558), so the file maintains itself exactly like its siblings.
- **Cold impact:** Removes ~851 of ~2,700 cold-remote round trips (~32% of request volume). Request-proportional share of the 203s remote gap is ~65s; thread-pool overlap makes attribution sublinear, so honest estimate: cold-remote 415s -> ~350-375s standalone (-40 to -65s). Near-zero effect on cold-local. Standalone value if tx.lock stalls; subsumed by it otherwise — but worth doing first because it is days of work and also shrinks the pack and the refresh job's request manifest by 45%.
- **Parity:** Strongest possible: synthesize all 851 responses from the table, byte-compare against the captured request/response corpus from the census (which already exists), and gate shipping on 851/851 exact match — the same parity-proof discipline that earned the H1-H3 subset its 'exact parity' result. The committed file is versioned, reviewable in diffs, and self-refreshing through the same mechanism the repo already trusts for SNOMED/LOINC displays.
- **Effort:** Small: days. The localFirst plumbing, the response-synthesis code, the byte-verification harness, and the request census all exist; new work is the extraction script and one file format.
- **Novelty:** H1-H3 implemented only the parity-provable subset and explicitly excluded UCUM because local computation can't match the curated table. The new move is refusing to compute: ship the table as data. It extends the repo's own committed-answer-file pattern rather than inventing a mechanism, which makes it the easiest sell upstream.

### Content-addressed memoization of local terminology evaluation (run-scoped pure-function store)
- **Mechanism:** The cold-local 240s vs warm-local 197s gap (~43s) plus the 60s 'study-design' stall are in-process: ValueSetValidator re-runs local expansion/membership per file because cache keys embed pretty-printed inlined VS content and per-request state defeats reuse (findings 'next frontier' items 2 and 4, diagnosed but not yet built). Bazel move: make evaluation keys derivation keys. Intern sha256-of-canonical-JSON once per ValueSet/CodeSystem object (stored on userData, invalidated never — these objects are immutable post-load), key = (vsHash, csHashes, paramsHash, code|expansion-op), value = the computed ValidationResult/expansion in a run-scoped ConcurrentHashMap. This replaces serialize-the-VS-per-call keying with an O(1) interned hash and makes the study-design VS expand once instead of per-referencing-file. Known trap from spike A's adversarial review: BaseWorkerContext copies expParameters per call, which made the first memo dead — the params hash must be computed from canonical content, not object identity.
- **Cold impact:** Cold-local 240s -> ~200s (-40s: the gap is precisely the engine work warm runs skip via the disk cache, and a content-keyed memo reaches the same hit rate without any persistence). Cold-remote also gains the in-process share, partially hidden by network overlap: ~20-40s. Stacked with tx.lock, this is what pushes the fully hermetic cold build toward the ~197s warm-local floor.
- **Parity:** Memoization of a deterministic pure function over hash-verified inputs — same inputs, same OperationOutcome, by construction. Run-scoped (in-memory only) so zero persistence, zero staleness, zero poisoning surface; nothing touches disk and the mutable-cache objection doesn't apply at all. Verification: A/B manifest diff plus the existing Errors=0/Warnings=3693 gate; spike A's multi-agent adversarial pass is the template for auditing the concurrency.
- **Effort:** Medium: builds directly on spike/core-txperf's lock-split and streaming hashJson; main risks are the expParameters-copy trap (already mapped) and the shared-SD-userData CME (already mapped, with the serial-retry fallback as a net).
- **Novelty:** Spike A memoized token *serialization* and fixed locking; this memoizes the evaluation *result*, which the findings list as diagnosed-but-unbuilt. Distinct from all network-side ideas: it is the only lever on the cold-local and warm budgets, and it compounds with everything above.

### Hermetic build gate: fail-on-network mode that turns pack completeness into a checked invariant
- **Mechanism:** -Dorg.hl7.fhir.tx.hermetic=true at the single network choke point already used for throttling (ManagedFhirWebAccessor.httpCall, where -Dorg.hl7.fhir.tx.maxConcurrency lives): any terminology network call either throws or logs-and-counts, and the build fails at the existing error gate with the exact list of missing derivation keys. CI runs the cold build hermetic against tx.lock; an empty miss list proves the pack is complete for this spec revision; a nonempty list is, verbatim, the input manifest for the refresh job (closing the loop with ideas 1-2). This is the Nix sandbox equivalent: hermeticity is enforced, not hoped for. Dev builds keep network fallthrough; only CI and benchmarks run sealed.
- **Cold impact:** 0s direct. Indirect: makes cold time deterministic — 415s ±40%-by-hour collapses to ~212s ±3% noise floor, which per the findings' own measurement meta-finding is the difference between measurable and unmeasurable for every future sub-100s optimization. Also guarantees zero tx.fhir.org load from CI cold builds (politeness ceiling reached).
- **Parity:** No output change whatsoever — it only forbids a class of I/O. If the pack is complete the build is byte-identical to a warm run; if incomplete the build fails loudly instead of silently going stale or slow. Strictly improves the parity story of every other idea by converting their completeness assumptions into assertions.
- **Effort:** Small: days. One flag, one choke point, miss-list reporting wired to the existing error gate, one CI job variant.
- **Novelty:** Nothing in the tried list addresses verification or completeness — every prior network idea (prefetch, batch, local-first) was best-effort with silent fallthrough. This is the piece that makes 'lockfile-style artifact' an honest claim rather than a renamed cache: a cache tolerates misses quietly; a lockfile that is allowed to be incomplete-but-checked is a different contract, enforced here.

### tx.lock — a committed, content-addressed terminology lockfile (npm-shrinkwrap for the cold build)
- **Mechanism:** An explicit `--tx-lock=refresh` run (serial, polite, off-peak) replays the full cold request set against tx.fhir.org and writes a deterministic artifact: entries of hashJson(canonical request) -> response, plus a header pinning {SNOMED/LOINC/UCUM edition versions, tx server software version}. This is literally the existing TerminologyCache on-disk format made immutable: fhir-core's CacheToken.key (TerminologyCache.java:491-616 in repos/fhir-core .../utilities/TerminologyCache.java) already hashes the full serialized ValueSet + expansion params + coding, so the key is a pure function of pinned inputs. Cold builds preload the lock as a read-only L2 layer in the TerminologyCache constructor (the load(folder) path already exists); misses still go live to the server and are reported at build end as 'lockfile drift' with a suggested refresh PR. Ordinary builds NEVER write the lock; the refresh script refuses to record any non-2xx or OperationOutcome-with-transient-error response, so cache poisoning is impossible by construction. Ship it either committed under tools/tx/ or as a sha256-pinned tarball fetched like a package dep. Size measured: full cold cache = 5.1MB gzipped; dropping the inlined VS request bodies (store key->response only) cuts snomed from 33MB raw to ~1-2MB.
- **Cold impact:** Covers all ~1,900 validateCode requests + ~800 $expand. Cold-remote becomes warm-remote by construction: 415s±40% -> ~212s deterministic (-200s, the entire remote cold tax, and the ±40%-by-hour variance and politeness exposure go to zero for normal builds). Cold-local 240s -> ~200s (preloaded entries also skip the residual in-process expansion grinding that makes up most of the 43s local cold/warm gap). This is the only idea whose endpoint is a measured number rather than an interpolation.
- **Parity:** Responses are the server's own bytes for the pinned editions; replaying them is identical to a warm cache hit, which is already the parity-verified path (Errors=0/Warnings=3693). Any spec edit to a ValueSet changes the request hash -> miss -> live request -> same answer as today. Drift (server edition bump) surfaces as a reviewed PR diff, not silent staleness. Verify with the existing judge.sh harness against a no-lock reference run.
- **Effort:** Medium: 2-4 days. Read-only preload mode + drift report in TerminologyCache, refresh script reusing runs/cold-run.sh capture, CI job that fails refresh on transient outcomes. No protocol changes, no server cooperation needed.
- **Novelty:** Differs from persistent disk caching (rejected as evil) on every poisoning axis: written only by an explicit refresh that rejects error outcomes, immutable between refreshes, keyed by edition pins not branch names, diffable in code review. Differs from the CI master.zip bootstrap (mutable, branch-keyed, silently stale). Differs from $batch prefill (zero runtime requests instead of reshaped ones — sidesteps the wallclock-negative lesson). Differs from cache-id (no protocol semantics change, so the H4 grammar-system wrongness cannot occur).

### $prepare-publication: content-addressed Terminology Answer Pack + tx.lock (the flagship)

### Content-addressed GET for $expand: memoization moved into the HTTP layer (cache-id done right)
- **Mechanism:** Server computes expansionKey = sha256(canonicalize(vsDefinition) + usedCodeSystemVersions + expansionParams) and serves GET /r5/expansions/{key} → the expansion ValueSet with Cache-Control: public, max-age=31536000, immutable, ETag=key. ## Lens: Compiler engineer: terminology answers are pure functions of pinned inputs (ValueSet definition, code-system edition, expansion params) — so compile them ahead of time into versioned, content-addressed artifacts whose staleness is detected by key-hash mismatch (miss → network fallthrough), never by trusting a cache. ### CRaC/CRIU checkpoint of the loaded-context JVM heap
- **Mechanism:** The ~80s loads phase deterministically computes a huge heap (parsed 931 examples, registered SDs, link-checker index, canonical managers). Checkpoint the JVM at the loads/produce boundary with CRaC (or out-of-band criu dump), keyed by sha256 of (classpath jars + source tree + fhir-settings). A build whose key matches restores in ~2-4s and proceeds. Two flavors: (a) same-key restore — exactly the CI pattern where one sha is built 2-3 times (PR run, merge run, release run) and the dev pattern of rerunning after infra/flag tweaks; (b) split-load — reorder loads so version-pinned immutable packages (r4b, extensions, hl7.terminology) load first and checkpoint there, valid across commits, then load the mutable source tree after restore. CRaC Resource hooks close the tx HTTP client and log handles at checkpoint and reopen on restore.
- **Cold impact:** Same-key restore: loads 80s → ~3s, so cold-local 240s → ~165s and cold-remote drops the same ~77s. Split-load flavor needs one measurement (what fraction of the 80s is pinned-package load vs source load) — if half, ~40s cross-commit. Stacks with everything else since no other idea touches the load phase.
- **Parity:** The restored heap is bit-identical to the checkpointing run's state, and checkpoint creation is gated on that run finishing clean (Errors=0, manifest match). Risk to audit: wall-clock values captured during loads that leak into published output (the manifest tooling already normalizes timestamps, so divergences would be caught by runs/judge.sh); RNG-seeded UUIDs in table scripts are already on the known-nondeterminism list.
- **Effort:** High: CRaC-enabled JDK (Azul/OpenJDK CRaC), Resource hooks for sockets/files, key computation, and a parity audit pass. Spike-able in a week with raw criu against a paused JVM before committing to CRaC integration.
- **Novelty:** Distinct from the AOT lens: AOT/CDS caches compiled code and class metadata; this snapshots computed application heap state. Nothing on the tried list touches process snapshotting, and it is the only lever on the 80s loads budget.

- **Novelty:** Answers the 'every CI build of the same commit asks identical questions' prompt without a shared cache: it is not incremental compilation (no cross-commit reuse, no invalidation burden) and unlike every tried item, it optimizes across builds rather than within one.

- **Cold impact:** Converts the dominant fork-contributor scenario from cold-remote 415s±40% to roughly warm-remote 212s plus a small delta for branch-specific questions: ~-180s for a few dozen lines of code. Highest impact-per-line on this list.
- **Parity:** The seed contains answers the build would have fetched anyway from the same server at the same pinned editions; misses fall through. The poison filter strictly improves today's behavior (currently a poisoned upstream zip would propagate). Honest caveat: this leans on the existing CI-published-zip mechanism the owner already tolerates — the seed itself is read-only and CI-regenerated per master build (lockfile-ish), but the local cache it seeds remains the status-quo mutable one.
- **Effort:** Trivial-to-low: a URL fallback plus a filter, ~1 day including a fork-simulation test.
- **Novelty:** Nobody proposed it: the 404 sits in the measured-facts list unexploited. It is the cheapest possible use of cross-builder determinism — piggybacking on infrastructure that already exists rather than building any.
